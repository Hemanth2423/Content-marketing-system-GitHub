# GitHub Developer Personas

## Persona 1: The Individual Developer

**Who they are:** A software developer working independently or on a small team. They use GitHub daily for personal projects, open source contributions, and professional work. They care deeply about their tools and have high standards for developer experience.

**Role:** Software developer, indie hacker, open source contributor, freelancer
**Experience level:** Mid to senior (3-8 years of coding experience)
**Team size:** Individual or 2-5 person team

**Primary goals:**
- Ship code faster without sacrificing quality
- Automate repetitive tasks so they can focus on creative problem-solving
- Stay current with tools and practices used by top engineering teams
- Build a public portfolio of work on GitHub

**Pain points:**
- Context switching between tools slows them down
- Setting up CI/CD pipelines is time-consuming for each new project
- Code review on solo projects feels disconnected — no one to review their work
- Finding good documentation for edge cases takes too long

**What they read:**
- GitHub blog (developer-focused posts, tutorials)
- Hacker News
- Dev.to, Hashnode
- YouTube tutorials
- Twitter/X for real-time developer conversation

**Content preferences:**
- Tutorials with real code examples they can run immediately
- Honest perspectives on tools — pros AND cons
- Short-form Twitter threads for quick insights
- Long-form blog posts for deep dives on specific topics

## Persona 2: The Engineering Lead

**Who they are:** A senior engineer or engineering manager responsible for a team of 5-20 developers. They make or influence decisions about tools, platforms, and workflows. They balance technical quality with delivery speed.

**Role:** Engineering manager, tech lead, senior staff engineer, principal engineer
**Experience level:** Senior (8+ years, often including management experience)
**Team size:** 5-20 direct reports or cross-functional peers

**Primary goals:**
- Improve team velocity without burning out developers
- Reduce security and compliance risk in the software supply chain
- Standardize tooling across the team to reduce coordination overhead
- Demonstrate engineering quality and governance to leadership

**Pain points:**
- Onboarding new developers takes weeks due to complex local setup
- Security vulnerabilities in dependencies are discovered late in the cycle
- Code review bottlenecks slow PRs to a crawl
- Inconsistent practices across team members create technical debt

**What they read:**
- GitHub changelog and product announcements
- Engineering blogs from companies like Stripe, Netflix, Shopify
- LinkedIn (for professional updates and case studies)
- Research reports (State of DevOps, DORA metrics)

**Content preferences:**
- Case studies showing how other engineering teams solved similar problems
- Product announcements framed around team impact, not individual features
- Data-backed arguments for tool adoption
- LinkedIn posts for professional sharing

## Persona 3: The Enterprise Buyer

**Who they are:** A CTO, VP of Engineering, or Director of Developer Experience at a large company. They are evaluating GitHub Enterprise for their organization of 500+ developers. They care about security, compliance, cost, and organizational change management.

**Role:** CTO, VP Engineering, Director of Platform Engineering, DevOps VP
**Experience level:** Senior leadership (15+ years, primarily strategic and organizational)
**Organization size:** 500+ developers, often 5,000-50,000 employee company

**Primary goals:**
- Reduce engineering tool sprawl and standardize on a platform
- Meet compliance requirements (SOX, GDPR, SOC 2, FedRAMP)
- Demonstrate ROI of platform investment to CFO and board
- Enable developer teams to move faster without creating security risk

**Pain points:**
- Fragmented toolchain across different teams and business units
- Security incidents traced back to insecure code practices or leaked credentials
- Difficulty demonstrating engineering productivity metrics to non-technical leadership
- Vendor lock-in risk when choosing a core platform

**What they read:**
- Gartner and Forrester analyst reports
- GitHub for Enterprises content and case studies
- LinkedIn
- Industry publications (CIO magazine, InfoQ, The New Stack)

**Content preferences:**
- Case studies with specific ROI metrics and enterprise peer examples
- Compliance and security-focused content
- LinkedIn for professional discovery
- Formal white papers for evaluation documentation

## Persona 4: The Open Source Maintainer

**Who they are:** A developer who maintains one or more open source projects on GitHub. They manage contributions from the community, handle issues and PRs from strangers, and often do this work in their spare time without compensation.

**Role:** Open source maintainer, project lead, foundation member
**Experience level:** Expert (10+ years, deep expertise in their project's domain)
**Community size:** Ranges from a few contributors to thousands (projects like React, Python, Linux)

**Primary goals:**
- Make contribution as frictionless as possible for new contributors
- Maintain code quality while scaling to many contributors
- Protect the project from security vulnerabilities introduced by outside code
- Sustain the project long-term without burning out

**Pain points:**
- PR review backlog — more contributions than time to review
- Malicious or accidental security vulnerabilities introduced by contributors
- Inconsistent code style and testing across contributions
- GitHub funding limitations for sustaining long-term maintenance work

**What they read:**
- GitHub blog (open source specific content)
- Open source community forums and mailing lists
- Twitter/X (where open source community conversation happens)
- GitHub Discussions on their own projects

**Content preferences:**
- Twitter threads for quick tips and community discussion
- Technical tutorials for specific GitHub features that help maintainers scale
- GitHub blog posts about open source sustainability and tooling
